- `DocumentsContract.renameDocument` 通常返回裸 `/document/<id>` URI；直接存库会丢 tree 前缀，之后 `getTreeDocumentId` 抛异常。必须用原 tree 重建 `buildDocumentUriUsingTree`。

- 判断"树根 vs tree 内子目录"用 `isDocumentUri(context, uri)`，不能用 `isTreeUri`（两者都返回 true）。

# 2026-11-26 01:40 — ColorOS 创建项目失败（用户真机反馈）

## 现象
一加 13 / ColorOS 17，选“我的文件”作为保存位置，Empty Project 报通用 IO 错误。

## 定位与改动
- 原错误把真实原因吞了：`createDocument` 抛的异常只保留了 message，UI 只显示通用文案。现在 `CreateProjectResult.Failure.detail` 会显示在创建页（“Details: …”），并 `Log.w(TAG="MobileIDE")` 记录阶段与异常。
- 模板写入不再“创建子目录后按新 URI 重新打开”：改为在同一个父 tree 会话里用相对路径写（OEM provider 常拒绝新子目录 URI）。
- `createEntry` 的创建后校验放宽：按 URI 查 → 父目录列表查 → 信任 `createDocument` 返回的 URI，避免 provider 回读差异被当成失败。
- 移除“用 FLAG_SUPPORTS_WRITE 判断目录可创建”的硬性拦截：公开 API 没有 FLAG_SUPPORTS_CREATE，目录标志不可靠，会误伤正常目录。仅保留失败后的提示区分。
- 提示文案：建议选真实子目录（如 Documents），不要选“我的文件”这类虚拟视图。

## 教训
- ColorOS/OPPO 的“我的文件”可能是聚合视图，列表可读但不可创建。
- SAF 创建子项后，尽量复用已有 DocumentFile/会话，不要重新按 URI 构造。

## 状态
- 25 个 JVM 测试通过，构建通过；真机行为仍待用户验证。
